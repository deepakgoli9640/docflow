# Decision Log

Lightweight ADRs. D1–D22 were **accepted** at the end of Phase 1 (D22: replace the DocFlow stub at the
repository root). Items marked ⚠️ deviate from the original brief and were explicitly approved.
Later entries record decisions made while implementing.

| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| D1 | Six business services + gateway; no auth/config/discovery servers | Separate auth service; Eureka; Config Server | Merchant-service owns credentials so it issues tokens; Docker/K8s DNS replaces Eureka; env vars + profiles replace Config Server. Fewer JVMs on 8 GB. |
| D2 | Async Kafka between services; local replicas for hot-path data | Sync REST between services | Availability isn't multiplied across services; ledger/notification outages don't block payments. Cost: eventual consistency, handled explicitly ([01 §4.3](01-architecture-overview.md)). |
| D3 | One sync internal call: notification → merchant for webhook secret | Put secret in events; asymmetric signing | Secrets must not sit in retained Kafka topics. Off the hot path, cached, retried. |
| D4 ⚠️ | **One Kafka topic per aggregate** (`payment.events.v1`) with event types inside, instead of one topic per event type | Topic per event type as suggested | Kafka orders only within one partition of one topic; per-type topics break per-payment ordering. The suggested names survive as event types. |
| D5 ⚠️ | **No separate `SUCCESS` state**; `CAPTURED` is success. `payment.success` folded into `PaymentCaptured`. | Keep both | Two states meaning "money collected" invite consumers to disagree. |
| D6 | Provider-evidence override: `EXPIRED`/`CANCELLED` → `CAPTURED` allowed only on provider-confirmed capture | Strictly terminal; auto-refund | Internal state must converge to where the money actually is; hospital decides on refund. |
| D7 | Transactional outbox with polling relay | Debezium CDC; publish after commit; Kafka transactions | Atomic with business write, no extra infra. CDC is the production upgrade (~1 GB for Kafka Connect). |
| D8 | JSON events with `eventVersion`, additive-only within a version | Avro/Protobuf + Schema Registry | Readable, one less container. Registry recommended for production. |
| D9 | Idempotency keys in Postgres | Redis | Must commit atomically with the business row. |
| D10 | Redis only for gateway rate limiting + suspended-merchant deny-list | No Redis; Redis caches everywhere | Both need shared, fast, TTL-based state across gateway replicas. Nothing else justifies it. |
| D11 | Merchant auth: OAuth2 client credentials → 15-min JWT (Spring Authorization Server in merchant-service) | Raw API key on every request (Razorpay style); Keycloak | Local validation, secret sent rarely, standard protocol; Keycloak costs ~500 MB. Deny-list closes the revocation gap. |
| D12 | Razorpay Orders + Standard Checkout on a minimal page we host | Payment Links; server-side card collection | Card data never touches us; supports manual capture. Payment Links are a valid later alternative. Server-side card collection is ruled out (PCI). |
| D13 | Raw `RestClient` adapter instead of Razorpay Java SDK | Official SDK | Explicit timeouts, Micrometer observation, WireMock-friendly base URL, our own error mapping. |
| D14 | One Postgres container, one database + one user per service | Container per service; shared schema | Enforces ownership with permissions while saving RAM. Production: separate instances. |
| D15 | `NUMERIC(19,2)` + `BigDecimal` `Money` value object | `BIGINT` paise | Matches the brief ("decimal types"); paise conversion confined to the adapter. |
| D16 | Optimistic locking + bounded re-apply; conditional `UPDATE` for refund reservation | Pessimistic locks everywhere | Low contention; the one real race (concurrent refunds) is solved atomically in SQL. |
| D17 | Ledger immutability enforced by app, DB grants and triggers; deferred balance trigger | App-only checks | Defence in depth for the one table that must never be wrong. |
| D18 | Blocking retries where order matters (ledger, replicas); retry topics for notifications; DB-scheduled retries for webhook delivery (hours) | One retry style everywhere | Each matches its ordering and delay needs. |
| D19 | Reconciliation reads internal data from ledger events; never writes to ledger | Read payment DB; auto-correct | Ownership rules; brief forbids automatic financial changes. |
| D20 | Jaeger for traces; Loki optional | Tempo; ELK | Simplest OTLP-native UI; ELK is far too heavy for 8 GB. |
| D21 ⚠️ | **Spring Boot 3.5.x** (as requested) | Spring Boot 4.x (the repo's current POM uses 4.1.0) | You asked for 3.x and most interview material targets 3.x. Note: 3.5 is the last 3.x line; check its open-source support window — moving to 4.x later is mostly dependency/namespace work. |
| D22 ⚠️ | **Repository layout**: the branch currently contains an unrelated "DocFlow" Spring Boot stub at the root | (a) Replace the root with the gateway project; (b) put the gateway in a sub-folder | Your call — see the Phase 1 summary. Docs are in `docs/` either way. |
| D23 | `platform/web-support` separate from `platform/common` | One shared module | `common` stays framework-free and usable by the reactive gateway; servlet plumbing (exception handler, filters) is auto-configured only in MVC services. |
| D24 | Spring Authorization Server with a **stateless** `OAuth2AuthorizationService` | Default in-memory or JDBC authorization store | The default in-memory store keeps every issued token forever (memory leak with client-credentials); JDBC adds a table we never read. Self-contained JWTs + no introspection endpoint = nothing to store. |
| D25 | JWT signing key from PEM files, else an **ephemeral** key with a loud warning | Commit a dev key; always require files | No key material in git; zero setup locally; production must mount real keys. |
| D26 | Max 2 active API keys; last active key cannot be revoked; merchant row locked (`SELECT … FOR UPDATE`) while checking the limit | Optimistic locking | Rotation without downtime; no self-lockout. The limit check reads child rows, so optimistic locking on the merchant would not detect the race — a concurrency test proves the lock works. |
| D27 | Gateway actuator on separate port 9080 | Same port with deny rules | Prometheus can scrape inside the network, while `/actuator` is not even served on the public listener. |
| D28 | Dockerfiles package a host-built jar | Maven build stage inside Docker | Avoids a second Maven cache on an 8 GB laptop; CI builds once. |
| D29 | `deploy/env/.env` is imported only under the `local` profile | Import unconditionally | Tests must not depend on a developer's machine (this bug actually happened, and a test caught it). |
| D30 | Pin `nimbus-jose-jwt` 9.47 in the parent POM; Maven enforcer `dependencyConvergence` on | Let Maven pick | Resource server and Authorization Server pulled different versions; the enforcer rule makes such conflicts a build error instead of a runtime surprise. |
| D31 | `Authority` (MERCHANT / PROVIDER / SYSTEM) separate from `TransitionSource` | One enum | Rules are about *who may*; history wants *where from*. Stale provider events are ignored, invalid merchant requests rejected. |
| D32 | Per-merchant PostgreSQL advisory lock around payment creation | Optimistic checks; SERIALIZABLE isolation | Daily-limit and key checks are check-then-act over rows that do not exist yet; row locks cannot cover them. Cost: one merchant's creations are serialised for a few ms. |
| D33 | After a signed checkout callback, fetch the payment from the provider immediately | Trust the callback; wait for webhook | The callback proves authenticity but not the final status (authorized vs captured); one cheap GET gives the patient a definite answer. |
| D34 | Provider order created outside the DB transaction; failure after commit still returns 201 CREATED | Hold the transaction open; return an error | Never hold DB connections across network calls; never tell a client "failed" about something that was committed. |
| D35 | JDK HttpClient forced to HTTP/1.1 for the provider | Default (attempts HTTP/2 upgrade) | The h2c upgrade broke POST bodies against a plain-HTTP server in tests; one predictable protocol beats multiplexing at our volume. |
| D36 | Simulated provider selected by property, logs a warning, labels the checkout page | Spring profile; no simulator | Lets the whole flow run without keys while making it impossible to mistake for a real integration. |
| D37 | Server-rendered checkout HTML with a CSP nonce, no template engine | Thymeleaf; SPA | Four tiny pages; fewer dependencies; strict CSP is easier to reason about. |
| D38 | `platform/persistence` shared module | Copy base entity/converter per service | Third service needing the same JPA plumbing; auditing and encryption behave identically everywhere. |
| D39 | Evidence ordering: successful attempts applied before failed ones | Arrival order | Prevents a spurious FAILED → "late capture" when a poll returns several attempts at once. |
| D40 | "ledger-service" implemented as **transaction-service** (history, status and ledger in one service) | Separate history service + ledger service | Both are built from the same events and answer the same merchant questions; one owner keeps history and postings consistent. |
| D41 | One active outbox relay per service via `pg_try_advisory_xact_lock` | ShedLock; no coordination (SKIP LOCKED only) | Two relays would publish one payment's events out of order; the advisory lock needs no extra table or dependency in the shared module. |
| D42 | Separate Kafka consumers per topic where blocking retry waits on another topic | One listener on both topics | A RefundCompleted retried in place while its capture is not booked would otherwise block the payment topic delivering that capture (dead-lock until the DLT). |
| D43 | Notification intake stores rows; delivery is a DB-driven dispatcher (lease + SKIP LOCKED, backoff + jitter) | Deliver inside the Kafka listener with retry topics | A slow hospital endpoint must never hold a partition; retries over hours belong in the database; every replica can dispatch safely. |
| D44 | Webhook URL re-checked against private/link-local addresses right before every delivery; redirects not followed | Validate only when the URL is saved | DNS can change after validation (rebinding); a redirect could point inside the network. |
| D45 | Dashboard as plain HTML/CSS/JS modules served by nginx, proxying to the gateway | React/Vite SPA; server-rendered pages in a service | No Node toolchain in the build or CI, no third-party code under a strict CSP, one origin (no CORS); the gateway and services stay the only place rules are enforced. |
| D46 | Dashboard sign-in with OAuth2 client credentials (API key / ops client), token in sessionStorage, secret in memory only | Add a user store + OIDC now | Reuses the existing auth model with no new backend; documented as a local-first simplification: production needs real user accounts (OIDC) in front. |
| D47 | OPS endpoints added for the dashboard: merchant configuration read, notification list/detail across merchants | Dashboard calls internal endpoints | Same role checks as every OPS API; the webhook secret is never returned. |
| D48 | Snapshot version = a `snapshot_version` column on `merchants`, incremented with `UPDATE … RETURNING` in the change's transaction | Use `updated_at` or the JPA `@Version` | Profile and configuration live in different tables; one counter on the merchant row orders every snapshot of a merchant, and the row lock serialises concurrent changes. |
| D49 | Merchants without a snapshot are backfilled at startup; OPS can republish all | One-off migration script | Upgrades need no manual step, and any replica can be rebuilt on demand (snapshots are full state, versioned, idempotent to apply). payment-service resets manually seeded replica versions to 0 so the first real snapshot wins. |
| D50 | Gateway deny-list entries expire after 20 min; the check fails open if Redis is down | Permanent entries; fail closed | New tokens are already refused by merchant-service, so an entry only has to outlive tokens issued before the suspension (15 min). Failing open keeps the edge available; payment and refund creation are still refused by the services' own replicas. |
| D51 | Scripts wait for replication with a throwaway probe payment (created and cancelled) | Fixed sleeps; a readiness endpoint | Asynchronous replication needs an observable condition; the probe uses only public APIs. A dedicated readiness endpoint would be cleaner if this becomes common. |
| D52 | Reconciliation's internal side comes from `TransactionCreated` (ledger), keyed by payment, carrying the provider reference | Read payment/refund events | The ledger is the record of money: a capture that never reached the ledger must show up as a difference. |
| D53 | Unsettled internal items are re-flagged in every batch until matched or resolved; a reference matched on another day is a duplicate | Flag once on the due date | No missed item if a day's report is never loaded; double settlement across days is caught. |
| D54 | Uploads: SHA-256 pass, then a streaming parse pass; matching in the background (202) | Load the file into memory; synchronous run | Files up to 20 MB never sit in memory; the HTTP request stays short. A stale-run job fails batches orphaned by a restart. |
| D55 | Gateway request-size limits per route instead of a default filter | One global limit | A route cannot loosen a default filter; only the settlement upload needs 21 MB. |
| D56 | The W3C `traceparent` is stored in the outbox envelope and sent as a Kafka header by the relay | Let the producer's observation create a new trace | The relay publishes later, on its own thread; without carrying the context the consumer side would start an unrelated trace. |
| D57 | Shared `platform/observability` module that sets defaults through an `EnvironmentPostProcessor` (default properties) | Copy the settings into every `application.yml` | One place for tracing, Kafka observation, histograms and log masking; any service can still override a value. |
| D58 | PII masking as a structured-logging value processor on every string field | Mask at each log call; a Logback converter | A safety net that cannot be forgotten; developers still must not log PII (the smoke test checks a planted email and phone never appear). |
| D59 | Counters named `*.initiated` / `*.queued`, never `*.created` | Keep `payments.created` | OpenMetrics reserves `_created`; Prometheus exported `payments_total` and the dashboards were empty. |
| D60 | Trace export off by default; metrics, logs and the obs stack fail open | Always export; fail on a missing collector | Local runs and tests need no Jaeger; observability must never take down payments. |
| D61 | Gateway uses the JVM DNS resolver (30 s positive cache) | Reactor Netty's resolver (honours the 600 s Docker DNS TTL) | A recreated container gets a new IP; the gateway returned 503 for minutes. |
| D62 | Webhooks older than 48 h are stored as `STALE` and acknowledged without being applied | Reject with 4xx; apply anyway | A 4xx makes the provider retry forever; applying a two-day-old event risks overwriting newer state. The inbox row keeps it auditable. |
| D63 | Database outage test stops a Postgres container bound to a fixed host port | Toxiproxy; pausing the container | A paused database leaves pooled connections hanging with no socket timeout; a restarted container normally gets a new random port. A fixed port keeps the same JDBC URL, no extra image. |
| D64 | Connection failures anywhere in the cause chain (SQLState 08xxx, connection exceptions, Hikari's "Connection is closed") map to `503` + `Retry-After` | Map only `CannotCreateTransactionException` | A dead pooled connection surfaces as "Unable to rollback"; it is an outage, not a bug, and the client should retry with the same key. |
| D65 | JaCoCo: unit and integration tests append to one file per module; CI prints a coverage table, no threshold yet | Aggregate module; fail under X % | Gives visibility without a gate that encourages coverage-chasing tests; a threshold can follow once the baseline is agreed. |
| D66 | Images built in CI from the jars of the test job, pushed to GHCR with the commit SHA and `latest`, only from master | Build in Docker with Maven; push from every branch | One build of what was tested; no registry noise from branches; the SHA tag is what a deployment pins. |
| D67 | Load test as an open model (constant arrival rate), spread over several hospitals; JDK runner next to the k6 script | Closed model (fixed users); k6 only | A closed model slows down with the system and hides queueing; the per-hospital rate limit would otherwise be what gets measured. The JDK runner needs no install. |
| D68 | Helm chart for the applications; PostgreSQL and Kafka from operators (CloudNativePG, Strimzi) or managed services | Bundle Bitnami Postgres/Kafka subcharts; plain manifests | Stateful systems need failover, backups and upgrades that operators already do well; the chart stays about the applications. |
| D69 | Each service receives only the secret keys it uses (`services.<name>.secrets`) | `envFrom` the whole secret | A compromised gateway pod must not hold Razorpay or encryption keys. |
| D70 | Kafka topics: replication factor and `min.insync.replicas` configurable, 3 / 2 in production | Rely on broker defaults | Topics are created by the services; making it explicit keeps `acks=all` meaningful (two copies before an event counts as published). |
| D71 | HA verified with two replicas per service in Compose plus static manifest validation | Claim HA from the manifests alone | The coordination (advisory lock, ShedLock, consumer groups, shared signing key) is what can break; it can be tested without a cluster. |
| D72 | `preStop` sleep of 10 s, `maxUnavailable: 0`, readiness from Spring's probe groups (no database in readiness) | Database in readiness | A database outage would mark every pod unready at once; the services already answer 503 with Retry-After. |
| D73 | People sign in through an identity provider (Keycloak, OIDC Code + PKCE); API keys stay for machines | Users and passwords in merchant-service | Password policy, lockout, MFA, directory federation and audits are what identity providers are built for; HPG keeps only authorization. |
| D74 | Services trust a second issuer, chosen by the token's `iss`, with its own rules (audience `hpg-api`, roles MERCHANT/OPS only, MERCHANT needs `mid`) | Let Keycloak issue any role; token exchange to HPG tokens | Keeps one token per request and no extra hop, while a compromised or misconfigured identity provider cannot mint SERVICE tokens or hospital tokens without a hospital. |
| D75 | Keycloak served under the dashboard's origin (`/auth/` proxied by nginx) | Separate auth domain with CORS | The dashboard's CSP stays `connect-src 'self'`; no CORS configuration to get wrong. |
| D76 | Access token in sessionStorage, refresh token in memory only; renewal by refresh or a silent `prompt=none` login | Everything in localStorage; a backend-for-frontend with cookies | Limits what an XSS could steal to a 5-minute token, with a strict CSP making XSS unlikely; a BFF is the stronger option if the dashboard grows. |
| D77 | Signing-key rotation by publishing retired public keys next to the active key; the active `kid` set in every token header | Swap the key in place | Swapping in place invalidates every token in flight; overlapping keys make rotation invisible to clients. |
| D78 | Settlement postings come from reconciliation (MATCHED payments only), booked once per payment | Book from the settlement report directly in transaction-service | Only reconciled money reaches the bank account in our books; mismatches stay with a person; repeats from later reports are harmless. |
| D79 | Disputes are their own aggregate and topic (`dispute.events.v1`); the payment stays CAPTURED | Add DISPUTED states to the payment state machine | The payment did happen; a dispute is a separate process with its own lifecycle. The 243-transition state machine stays untouched. |
| D80 | Chargeback postings follow the money the provider moved (`amount_deducted`), not the dispute status alone | Book at LOST only | Razorpay usually deducts when the dispute opens; the ledger must match the provider balance at every moment for reconciliation. |
| D81 | Refunds refused while a dispute is open | Allow and let the provider reject | A refund plus a lost chargeback would pay the patient twice; the rule is explicit and testable. |
| D82 | SMS through a provider port: `log` locally, MSG91 with DLT templates in production; texts carry amount and bill reference, no links | Twilio; free-text SMS | Indian regulation (TRAI DLT) requires registered templates; links in payment SMS look like phishing. |
| D83 | Dispute accept/contest require an Idempotency-Key, stored with the dispute update; repeating an already-made decision under a new key is a success | Rely on the status check alone (409 on repeat) | A client whose first call timed out needs the original answer, not a 409; the provider must never receive the decision twice. Same contract as capture and cancel. |
